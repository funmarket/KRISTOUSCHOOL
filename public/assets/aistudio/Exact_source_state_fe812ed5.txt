AppContext is explicitly declared a transition owner
This is one of the most important additions.

Current evidence:

src/context/AppContext.tsx = approximately 1,814 lines.

The new structure document does not say “delete AppContext.”

Instead it defines a safe decomposition path.
Phase A — stop making it larger
No new feature persistence/business logic should be added directly to AppContext.
Phase B — move domain composition gradually
As a domain is verified, composition can move toward focused hooks/providers such as:
useIdentitySession()
usePreferences()
useNotifications()
useMessaging()
useParentNotes()
useCalendar()

These are architectural examples, not automatically authorized files.
Phase C — AppContext becomes shell composition
Eventually AppContext should only coordinate genuinely application-wide state.

It should not remain the permanent school business database.

Public/private boundary is explicit
The document now protects us from one of the exact problems we discovered during DB-01.

An authenticated administrator may legitimately have broad RLS access.

That does not mean:
listPublicDirectory()

may expose unpublished directory entries.

A function whose contract says “public” must encode its own published-only boundary.

That principle applies to:
- directory;
- public content;
- food menu;
- calendar/public events;
- other anonymous reads.
Malformed success is explicitly forbidden
Because Messaging, Preferences and Parent Notes all exposed this defect class, the architecture now treats it as a global rule.

A domain must never:
String(undefined)

or:
missing id → ""

or:
missing nested result → READY

or:
child query fails → valid empty data

Malformed backend responses must fail closed.
Database/RPC/Edge Function responsibilities are separated
The document explains:
Direct RLS-scoped queries
Good for simple caller-scoped reads where RLS is the correct boundary.
RPCs
Use for:
- transactional invariants;
- quotas;
- locks;
- governance;
- privileged mutations;
- server-derived actor identity;
- multi-row state transitions.
Edge Functions
Use for true transport/integration boundaries such as:
- username authentication transport;
- Telegram initData verification/link/re-entry.
Not as a generic place to move arbitrary JavaScript.
Cross-domain transactions
A particularly important new rule is:
A domain can reference another domain's ID, but it may not duplicate the other domain's state.

Example:
parent_notes.student_id

references the student.

It does not make Parent Notes the owner of student identity.

For genuine multi-domain atomic operations:
Browser request 1
Browser request 2
Browser request 3

must not be presented as a transaction.

There should be one explicit server-owned transactional operation.
