## 2. Acceptance contract - product behavior that MUST NOT regress

### 2.1 Protected frontend/UI invariants

- Sign-in/sign-up modal is unchanged in layout, tabs, fields, seven role options, position, required data handling and credentials semantics. Choosing a privileged requested role must NEVER grant authority.
- Optional Web-to-Telegram account linking remains a one-time expiring code with signed `initData` and atomic user association. Browser and Telegram use the SAME canonical product data; no automatic identity merge.
- Public anonymous browsing works without an account, including within Telegram. No `GENERAL_USER` registered or fallback role.
- Eight existing role homepages are retained; owner role inspection does NOT impersonate another actor. Role tab checks help UX but never replace server authorization.
- Current design, card hierarchy, navigation and responsive behavior are source truth, especially Owner menu **Teachers -> Classes -> Registration**, stable-LTR Navbar and current FR/EN/AR texts/themes. Adding necessary account/academic operations must fit existing card/layout patterns; no restyle or large page redesign.
- `mockData.ts` remains available for tests and local screenshots, but production-like private data loads never fallback to it when server state is missing or denied. Distinguish loading, empty, error, unauthorized and unavailable states.

### 2.2 Authority hierarchy fixed by Product Owner

- `APP_ADMIN`: sole app Owner governance. May appoint another `APP_ADMIN` or `MANAGER`; can manage all ordinary accounts. Protect at least one recoverable Owner.
- `MANAGER`: operational actions, including ordinary account review, only with explicit delegation. Never gains `APP_ADMIN`/`MANAGER` appointment/governance by a broad `FULL_ACCESS` label.
- `ADMINISTRATIVE_PERSONNEL`: automatically gets complete normal operational school-administration rights and ordinary account lifecycle actions once APPROVED. No extra responsibility-group delegation. Can approve, reject, suspend, revoke, and reactivate **other** ordinary school accounts, including other `ADMINISTRATIVE_PERSONNEL`, but **cannot act on own account** and cannot govern any existing or requested `APP_ADMIN`/`MANAGER` authority.
- `TEACHER`: assigned classes only. `PARENT`: verified linked children only. `STUDENT`: own enrolled class only. `SCHOOL_STAFF`: no implicit universal roster, governance, or physical Pickup release.
- Public/anonymous: approved public pages only, no app role/account.
- Approval and reactivation must **not** grant access on the basis of requested role alone, an unchanged old token, an unverified relationship, or a client-supplied actor ID.

### 2.3 Domain ownership constitution

| Durable concept | Write owner | Not owned by |
| --- | --- | --- |
| Auth users / credentials / sessions / Telegram identity & link | Identity & Authentication (Supabase Auth plus controlled link) | Any feature frontend / Academics / Pickup |
| Account approval, active role, Manager grants | Access Control | School enrolment / UI request data |
| School student and staff profile identity | People | Auth credentials / class roster UI |
| Verified guardian-to-student link | Family | App signup / Admissions / Pickup |
| AcademicYear, Level, Class, TeacherClassAssignment, StudentClassMembership | Academics | Enrollment / community / UI |
| EnrollmentApplication, student Enrollment, requirements/documents | Enrollment | Academics class membership |
| ParentNote & reply | Parent Notes | Generic messaging/client state |
| Class question/reply and class content | Class Community | Membership or Auth identity |
| DismissalPolicy, AuthorizedPickupPerson, daily cycle, arrival/release events | Pickup | Parent profile, teacher dashboard or Notifications |
| Outbox delivery / notification inbox | Async/Notifications | Source business event authority |
| Public directory/menu/school pages | Respective Directory/Food/Public Content domain | Private profile/academic base table |

One owner per concept. An Academics roster projection may join authorized student/enrollment/guardian information for display, but does not become the owner of those identities/relationships. A TeacherClassAssignment is different from an account's `TEACHER` role.

### 2.4 Academic record entry and import, approved at product level

- Authorized `APP_ADMIN`, automatically authorized `ADMINISTRATIVE_PERSONNEL`, and capability-authorized `MANAGER` can maintain school academic data. Preserve existing `Classes` UI.
- **Two methods** must be supported: (a) individual add/edit forms; (b) `.xlsx` and `.csv` import with preview and confirmation. BOTH invoke the SAME verified domain validation and writer boundaries. Proposed UI details are subject to visual regression review.
- Importing an existing child/student is NOT school admission, creating a login, role approval, or parent linking. Duplicates, conflicts, incomplete rows, invalid class/teacher references and malicious spreadsheet content must fail safely and be visible before commit.
- `TEACHER` sees only assigned-class rosters via Teacher-specific data access; do not grant the school-wide Classes admin query to every Teacher. `PARENT` sees only linked children. No private rosters in public pages.

### 2.5 Pickup safety invariant, permanently mandatory

`WAITING -> PARENT_ARRIVED -> RELEASED`, with server-controlled `Africa/Tunis`/class dismissal windows. Parent announces arrival; authorized staff physically verify collector and confirm release via narrow server operation. Arrival cannot release; denied, duplicate, stale, concurrent and cross-class requests must be fail-closed. Durable audit and source-of-truth DB are required; realtime/notifications are projections, not authority. **Pickup button remains locked until full isolated+staging safety acceptance.**

## 5. Domain contracts and proposed interfaces (review before implementation)

### 5.1 Server-derived actor model

The backend authorizes a canonical actor using session/validated Telegram proof plus live account status, active role assignments, scoped grants and resource relations. A **requested** role is never effective authority. Avoid a frontend `role: AccountRole` field as a substitute for approval.

Proposed frontend-facing read model, conceptually (NOT committed code):

```ts
type AccountState = 'PENDING' | 'APPROVED' | 'REJECTED' | 'REVOKED'; // DG-01 may add SUSPENDED
interface CanonicalActorSnapshot {
  id: string;
  approvalStatus: AccountState;
  requestedRole: AccountRole | null;
  effectiveRole: AccountRole | null; // null unless approved and role assigned
  capabilities: string[]; // derived server-side, includes automatic admin bundle
  linkedChildrenIds: string[]; // server-verified Family relations only
  assignedClassIds: string[]; // server-verified Academics assignments only
}
```

This conceptual snapshot is separate from client-supplied sign-up data and does not dictate replacing the existing `User` interface without reviewed compatibility tests. Privileged operations must re-check live DB authority independently of any cached snapshot.

### 5.2 Administrative account operations

Recommended domain operation names (subject to packet-level interface freeze):

```ts
type OrdinaryRole = 'ADMINISTRATIVE_PERSONNEL' | 'TEACHER' | 'SCHOOL_STAFF' | 'PARENT' | 'STUDENT';
type AccountDecision = 'APPROVE' | 'REJECT' | 'SUSPEND' | 'REVOKE' | 'REACTIVATE';
interface ReviewAccountCommand { targetUserId: string; decision: AccountDecision; reasonCode?: string; expectedVersion: number; }
interface OwnerAppointmentCommand { targetUserId: string; appointedRole: 'APP_ADMIN' | 'MANAGER'; expectedVersion: number; }
```

- Actor identity must come from verified session, not `actorId` in the request. Exactly one atomic account-state/role mutation plus append-only audit per accepted decision; use optimistic version/conditional update and idempotency as required by real concurrent flows.
- Ordinary review denies any `APP_ADMIN`/`MANAGER` target or requested privilege elevation. Also deny Admin Personnel self-target actions; Owner-only appointment goes through a DISTINCT policy operation, not a `decision` parameter any staff member can abuse.
- Preserve last valid Owner, existing identity rows and Telegram link. Do not physically delete accounts on ordinary revocation; disabling access is not deleting person records or academic memberships.
- Approved Admin Personnel standard permissions are server-derived from effective active role; Manager delegated grants are separate. Do not copy role strings into `capabilities` and call that a capability store.

### 5.3 Academics/People/Family/Enrollment interfaces

Core domain concepts (naming proposals, not deployed tables):

- **People:** `Student` record with immutable stable `studentId` and school-approved `studentCode`; optional verified account link distinct from student existence. Teacher/staff people profile may link canonical Auth user after verified association.
- **Academics:** `AcademicYear`, `Level`, `SchoolClass`, `TeacherClassAssignment`, `StudentClassMembership`. Only Academics can establish/change class membership or assigned Teacher, and must verify Enrollment eligibility and correct year/level.
- **Enrollment:** `EnrollmentApplication`, `Enrollment` eligibility. Accepted application -> enrollment decision does not itself write Academics membership. Enrollment invokes one narrow Academics command, not direct writes to foreign tables.
- **Family:** `ParentChildLink` is verified, school-approved and scoped; no automatic link via same surname/contact.
- **Read models:** `SchoolClassSummary` and `ClassStudentRosterItem` already exist in `src/types.ts`; maintain these contracts for existing `ClassesManagementView`. Roster fields are projected from authorized owners and filtered to the caller's scope.

Proposed operation surface (freeze later):

```ts
interface SchoolAcademicReadPort {
  listSchoolClasses(filters: { academicYearId?: string; levelId?: string; query?: string }): Promise<SchoolClassSummary[]>;
  getClassRoster(classId: string): Promise<ClassStudentRosterItem[]>;
  listMyAssignedClasses(): Promise<SchoolClassSummary[]>;
}
interface AdminSchoolRecordsPort {
  createOrEditStudent(input: ValidatedStudentDraft): Promise<{ studentId: string }>;
  assignTeacherToClass(input: ValidatedTeacherAssignment): Promise<void>;
  establishClassMembership(input: VerifiedEnrollmentPlacement): Promise<void>;
}
interface FamilyReadPort { listMyLinkedChildren(): Promise<LinkedChildSummary[]>; }
```

`ValidatedStudentDraft`, `ValidatedTeacherAssignment`, `VerifiedEnrollmentPlacement`, `LinkedChildSummary` are **proposed packet-level types** whose exact fields must come from approved school forms and canonical model; do not create competing authority or ship these placeholder types without definition.

### 5.4 Spreadsheet import design contract

1. Staff picks canonical domain and template. Browser parses `.xlsx` or `.csv` in a bounded, explicitly reviewed tool chain; no hidden file uploads, macro execution, formula evaluation or external data enrichment.
2. Preview shows row totals, field-level validation, duplicate/conflict candidates, suggested *explicit* actions (create/update/skip/reject), academic-year/class references and write effects. Never silently guess identity matches.
3. Authorized staff confirms an exact preview fingerprint, domain scope and operation ID; backend revalidates every row and permissions at commit time. Reject mutated preview data, stale target rows, unauthorized actor, huge files and dangerous cell content.
4. Domain writers persist only their own records and append audit. Teacher assignments, enrollment and guardian links are distinct explicitly reviewed operations, not side effects of simply importing a student.
5. For retries: idempotency, duplicate prevention and clear per-row/atomic outcome contract. No silent partial success, no unverified `Saved` notification.
6. Imported records never create Supabase Auth credentials, assign `APP_ADMIN`/`MANAGER`/ordinary roles, auto-approve accounts, auto-link guardians, or modify Pickup release authority.

### 5.5 School admission and Parent/Teacher projections

- `RegistrationView` is a student admission intake, **not** app signup. It must not say an application was saved until a durable Enrollment command confirms success. Public intake must be abuse-resistant and store any protected documents privately.
- Parent home uses server-verified Family links and active class membership; empty links show an honest empty state. Teacher home uses active TeacherClassAssignment and class-scoped operations; no mock fallback or direct school-wide query.
- The Owner's Classes roster is a read projection, not an alternative source of enrollment truth. Provide staff proper data from Academics/People/Family with tested SQL RLS or guarded RPC.

### Review focus: five high-risk input classes

1. **Privilege escalation:** signup requested `APP_ADMIN`/`MANAGER`, forged `requested_role`, mixed active roles, ordinary Admin reviewing another Owner, self-target request, session-after-revocation -> all denied server-side (F1-G2/G3/G4).

3. **Resource scope:** Teacher asks another class; Parent asks unrelated child; Staff guesses roster ID; anonymous visitor calls direct RPC -> denied with zero unintended row leakage (F2-A2/A3/A5/A8).
4. **Cross-device state:** Browser and Telegram use same linked user, stale role status and repeated arrival requests; invalid Telegram link or old token -> safe identity/authorization, no duplicate state (F1-G5/F4-P2/P3).
5. **Misleading success:** admission, Parent Note or student question when backend offline/denies/validation fails -> no `saved`, `delivered` or `released` UI unless durable service confirms it (F3-C1/C2/C3/F4).
